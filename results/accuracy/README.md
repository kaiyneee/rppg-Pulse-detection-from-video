# Точность оценки пульса

Этап после исправления частоты дискретизации (`results/fs_fix/`).

## Итог

Умолчание теперь — пресет **`fft_spectral_mean`**: периодограмма полного
10-секундного окна (`frequency_method = fft`) и усреднение нормированных
спектров трёх областей лица (`roi.spectral_combination = "spectral_mean"`).
Прежняя конфигурация, на которой получены обе статьи, — пресет
**`legacy_welch8`** (Уэлч с одним 8-секундным сегментом, один ROI с
наибольшим SNR); состояние кода до смены умолчаний — git-тег `papers-v1`.

## Основной эталон

Контактная пульсовая волна на ПОЛНОМ 10-секундном окне, один фиксированный
способ (`benchmark/reference_full10s.py`, версия `full10s-v1`). Все
параметры заморожены константами в этом модуле и не читаются из
`PipelineConfig`, поэтому от настроек оценщика эталон не зависит. Посчитан
один раз для всех 2923 окон и сохранён в
`results/reference/ubfc_ref_full10s.csv` (файл версионируется в git,
несмотря на общее правило `*.csv` в `.gitignore`).

Как считается для окна, заканчивающегося в момент t_end:

1. отсчёты контактной волны с меткой в [t_end − 10 с, t_end];
2. приведение к равномерной сетке линейной интерполяцией на N точек между
   первой и последней меткой окна (N — число исходных отсчётов), частота
   fs = (N − 1) / (t_last − t_first). Нужно потому, что во втором
   подмножестве UBFC шаг прибора гуляет от 0,010 до 0,223 с;
3. детренд Тарвайнена со срезом 0,1 Гц (λ пересчитывается под fs волны),
   полосовой Баттерворт 4-го порядка 0,7–4,0 Гц нулевой фазы, z-нормировка;
4. периодограмма всего окна с окном Ханна, дополнение нулями до степени
   двойки с шагом сетки не грубее 0,05 уд/мин;
5. эталон — частота максимума в полосе 0,7–4,0 Гц (42–240 уд/мин).

В файле есть также доля мощности полосы в ±3 уд/мин от пика — мера чистоты
контактного сигнала. Старый эталон первой статьи (Уэлч, один 8-секундный
сегмент) остаётся только для сверки со статьями: в `eval_ubfc_subject.py`
его метод теперь заморожен параметром и не меняется вместе с оценщиком.

## Абляция 2×2

Против основного эталона; сквозное воспроизведение пайплайна, у каждого
варианта свои флаги публикации. MAE — по опубликованным окнам внутри
записи, затем среднее по записям. **Грубый промах — опубликованное окно с
|оценка − эталон| > 5 уд/мин**; доля — от всех опубликованных окон части.

| вариант | dev MAE | dev промахи | test MAE | test промахи |
|---|---|---|---|---|
| старая (Уэлч 8 с, один ROI) | 1,693 | 3,86 % | 1,754 | 4,44 % |
| только полное окно | 1,412 | 2,80 % | 1,280 | 2,80 % |
| только усреднение ROI | 1,734 | 4,01 % | 1,733 | 4,10 % |
| обе (новое умолчание) | 1,139 | 2,09 % | 1,236 | 2,68 % |

Основной выигрыш даёт полное окно. Усреднение спектров областей поверх
полного окна на dev лучше у 14 записей из 20 и хуже у 2 (медиана −0,037,
p = 0,014), но большой средний прирост там почти целиком даёт одна запись:
`subject27`, где одно полное окно проваливается до MAE 8,50, а с
усреднением — 3,80. На test усреднение лучше у 16 из 30 и хуже у 11
(медиана −0,025, p = 0,24, не значимо). Его роль — защита от катастроф,
когда выбор одной области цепляет шум, и меньше грубых промахов.

## Как использовались dev и test

- Разбиение зафиксировано заранее правилом, не зависящим от ошибок записей
  (`benchmark/experiments.py::split`): dev — 6 прежних настроечных записей
  DATASET_1 и каждая третья запись DATASET_2, test — остальные 30.
- **До** введения разбиения я смотрела агрегированные ошибки всех 50 записей
  из выгрузок первой статьи (какие записи худшие, гипотезы об отставании,
  часах, SNR). Ни одна настройка по этим данным не выбиралась — они только
  дали гипотезы.
- **После** введения разбиения все варианты отсеивались только по dev:
  отбеливание спектра, многооконный метод, учёт гармоники, методы
  извлечения и их смеси, мелкие участки, веса областей, Витерби, окно POS,
  кривые порога публикации, сверка эталонов, синхронизация.
- Test запускался **один раз** для решения — штатный вариант против
  финальной конфигурации, уже после того как она была выбрана.
- Test-колонки абляции и таблицы порогов чистоты посчитаны позже, по вашему
  запросу, для уже зафиксированной конфигурации; ни на что не влияли.
- Подготовка данных (кэш сигналов, эталоны, побитовая сверка
  воспроизведения) шла по всем 50 записям, но без просмотра метрик.

## Порог чистоты спектра

Отдельная жёсткая проверка (`QualityConfig.min_spectral_purity`), а не
слагаемое композитного балла Q; **по умолчанию выключена**. Чистота — доля
мощности полосы в ±3 уд/мин от пика того спектра, по которому получена
оценка пульса (при `spectral_mean` — объединённого). Окно публикуется,
только если чистота не ниже порога; порог — абсолютное значение доли.
Для каждого порога пайплайн воспроизводился заново: решение о публикации
влияет на доверенную историю пульса и через неё на следующие окна.

## Воспроизведение статей

```bash
PYTHONPATH=src venv/bin/python3 benchmark/reproduce_papers.py --paper 1   # ~1 ч
PYTHONPATH=src venv/bin/python3 benchmark/reproduce_papers.py --paper 2   # ~7 ч
```

Обе команды работают на пресете `legacy_welch8`, пишут результаты в
`results/reproduce/paper<N>/` и имя пресета — в `run_meta.json`.
`eval_ubfc_subject.py`, `degenerate.py`, `run_on_video.py` и
`run_webcam.py` принимают `--preset`.

Проверка: на пресете legacy_welch8 обе команды проверены на подвыборке и совпали с выгрузками статей побитово. Статья 1 (`--paper 1 --records 10,subject5`): пооконные выгрузки обоих режимов совпали с results/fs_fix/after по всем 14 общим колонкам, mae_pub идентичен; добавилась одна колонка bpm_ref_full10s. Статья 2 (`--paper 2 --records 6,10 --conditions G0,A2,B1f,D1`): 8 пар, 424 строки совпали с results/degenerate_v2, sha256 6dc601ff6f365202ab48b5f7… — тот же, что в проверке задания 4. Кроме того, воспроизведение из кэша на legacy_welch8 совпадает с прогоном первой статьи на всех 50 записях (2923 окна). Полные прогоны (~1 ч и ~7 ч) не повторялись

## Изменения в коде

- `config.py` — пресеты (`PRESET_OVERRIDES`, `make_pipeline_config`), новые
  умолчания, поле `preset`; `QualityConfig.min_spectral_purity` (выкл.);
- `config_io.py` — конфиг без поля `preset` достраивается от
  `legacy_welch8`, а не от текущих умолчаний: старые конфиги экспериментов
  сохраняют смысл;
- `quality.py` — `spectral_purity` и жёсткий гейт чистоты в `is_reliable`;
- `pipeline.py` — чистота считается по спектру, породившему оценку;
- скрипты — `--preset`; `eval_ubfc_subject.py` — эталон статьи заморожен,
  колонки `bpm_ref_full10s` и `mae_pub_full10s`, `--out-dir`, метаданные;
- тесты — 111 проходят.

## Ошибка в метаданных второй статьи (исправлено на будущее)

В `results/degenerate/run_meta.json` и `results/degenerate_v2/run_meta.json`
записано `git_commit: null` с пояснением «рабочая копия не под git». Это
неверно: `rppg_ptsd` — git-репозиторий, а я проверяла родительскую папку.
Хеш исходников `src_sha256` в этих файлах корректен и код идентифицирует.
`degenerate.py` теперь пишет настоящий коммит и флаг `git_dirty`; старые
файлы не переписывались.

## Попутно найдено (не исправлялось)
