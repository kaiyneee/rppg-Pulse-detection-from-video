# rPPG-PTSD: модуль бесконтактного измерения пульса и ВСР для исследования физиологических маркеров ПТСР

[![CI](https://github.com/kaiyneee/rppg-Pulse-detection-from-video/actions/workflows/ci.yml/badge.svg)](https://github.com/kaiyneee/rppg-Pulse-detection-from-video/actions/workflows/ci.yml)

Независимая, модульная реализация классических алгоритмов rPPG/HRV
(Balakrishnan et al., CVPR 2013; de Haan & Jeanne, IEEE TBME 2013; Wang et
al., IEEE TBME 2016; и др. — полный список в [CITATION.cff](CITATION.cff)),
построенная на MediaPipe Face Landmarker (Tasks API). Полный разбор
архитектурных решений, научная новизна и экспериментальный протокол — в
**[docs/research_report.md](docs/research_report.md)**. Этот README —
только установка, быстрый старт и обзор того, что реально есть в коде на
сегодня. См. также [CITATION.cff](CITATION.cff) для цитирования.

**Текущий результат на UBFC-rPPG (50 записей, эталон — контактная
пульсовая волна): MAE 1.67 ± 0.70 BPM при покрытии 98.9%**, бутстрэп 95%
ДИ [1.49, 1.87]. Подробности, проверка на переобучение и способ
воспроизведения — в разделе ["Валидация и бенчмарки"](#валидация-и-бенчмарки).

> **Лицензия.** Код закрыт — лицензия не предоставлена, все права защищены
> автором. Публичная видимость репозитория (если он публичный) не даёт
> права использовать, копировать или распространять этот код без прямого
> разрешения автора.

> **Рамка исследования.** Это модуль бесконтактного измерения физиологических
> маркеров (BPM, HRV), потенциально релевантных для исследований ПТСР — а
> НЕ инструмент диагностики или скрининга. HRV/RMSSD/LF-HF — неспецифичные
> физиологические корреляты, не диагностический критерий (см.
> research_report.md, раздел 7).

## Возможности

- Детекция лица: MediaPipe **Face Landmarker** (Tasks API), landmark-точки + поза головы. Версия модели зафиксирована (`float16/1/`, не `/latest/`) — см. "Установка".
- Динамические ROI: лоб, левая щека, правая щека, с occlusion-гейтингом на уровне пикселей и skin-маской (YCrCb).
- 6 методов извлечения сигнала с runtime-переключением: `GREEN`, `CHROM`, `POS`, `PCA`, `ICA`, `HEAD_MOTION`.
- **`--method auto`** — адаптация к разным камерам/освещению: вместо одного фиксированного метода КАЖДОЕ окно заново оценивает все 5 цветовых методов по фактическому spectral SNR на текущей камере и использует победителя (`RPPGPipeline._select_auto_method`). Разные сенсоры/условия объективно благоприятствуют разным классическим методам — единого метода, лучшего всегда и везде, в rPPG-литературе нет.
- **SQI-взвешенный fusion** (опционально, `FusionConfig.enabled`): вместо argmax-выбора одного ROI — объединение сигналов 3 ROI и head-motion канала с весами по spectral SNR и выравниванием фазы/знака между модальностями (`src/rppg/signal/fusion.py`). См. `scripts/compare_fusion_vs_argmax.py` для сравнения с argmax на синтетике.
- Препроцессинг: Tarvainen smoothness-priors detrending (λ откалибрована под fs=30 Гц, а не взята из HRV-литературы не глядя — см. `scripts/analyze_tarvainen_lambda.py`), z-score нормализация, Butterworth bandpass (zero-phase).
- 3 метода частотного анализа: `FFT`, `Welch` (по умолчанию), `Lomb-Scargle` (последний — для неравномерно дискретизированных данных после удаления окклюдированных кадров). Плюс `harmonic_sum` (сумма мощности на f/2f/3f вместо argmax по одному пику) — реализован, но по умолчанию ВЫКЛЮЧЕН: на внутренних данных он проигрывал Уэлчу по устойчивости траектории, см. [docs/welch_vs_harmonic_sum_verdict.md](docs/welch_vs_harmonic_sum_verdict.md).
- **Signal Quality Index**, 4 компоненты: спектральный SNR (со штрафом за гармоники/субгармоники), межзонное согласие, стабильность landmark-точек (нормирована на межзрачковое расстояние — абсолютная, не самоотносительная нормировка), устойчивость BPM между соседними окнами (temporal consistency). Плюс отдельный жёсткий гейт на мерцание освещения через фоновый ROI. Низкое качество → BPM/HRV не публикуются (`publishable=False`).
- HRV-признаки: Mean HR, SDNN, RMSSD, pNN50, pNN20, LF/HF, с суб-сэмпловой интерполяцией пиков и маскированием эктопических интервалов.
- **Двухпроходный офлайн-режим** (`--two-pass`, включён по умолчанию в `run_on_video.py`): окна, которым в причинном проходе не хватило истории для выбора между `f`, `2f` и `f/2` (холодный старт), пересматриваются против истории ВСЕЙ записи — `rppg.pipeline.apply_second_pass`. Сигнал при этом не пересчитывается и по времени не сглаживается, меняется только выбор кандидата. Для реального времени режим недоступен по построению (`--no-two-pass` — прежнее строго причинное поведение).
- Оценка частоты дыхания по амплитудной модуляции пульсовой волны.
- Опциональное ускорение Numba (POS, ~80x на этой машине — см. `scripts/benchmark_performance.py`), заготовка под ONNX Runtime для обучаемого метода.
- Объективная оценка тона кожи по ITA (без ручной Fitzpatrick-разметки) для стратифицированного анализа — `benchmark/skin_tone.py`.
- Структурированное JSONL-логирование по окнам (`--log`, см. "Быстрый старт") и один YAML/JSON-конфиг на эксперимент, сохраняемый рядом с результатами (`rppg.config_io`).
- **`PTSDPulseFeatures.best_effort_bpm`** — ВСЕГДА реальное число (никогда NaN), для встраивания как одной из фич в более крупную систему, которой на каждом шаге нужно значение, а не иногда "нет данных", и которая сама не ставит диагнозов по этому признаку. Зажат в правдоподобный диапазон и ограничен по скорости изменения между шагами (`BestEffortConfig`), поэтому не транслирует шумовые выбросы вроде скачков между 50 и 150 BPM на слабом сигнале — но это НЕ замена валидированной паре `bpm`/`publishable`: для научного/клинического использования нужны именно они, а не эта фича.

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt   # точные версии (==) — см. requirements.txt

# Модель Face Landmarker скачивается один раз (~3.6 MB), версия ЗАФИКСИРОВАНА

  https://storage.googleapis.com/mediapipe-models/face_landmarker/face_landmarker/float16/1/face_landmarker.task
```

`requirements.txt` зафиксирован точными версиями (`==`), реально протестированными
в этом репозитории на Python 3.9.6 — CI (`.github/workflows/ci.yml`) дополнительно
прогоняет те же пины на Python 3.9/3.11/3.12 как smoke-test совместимости.

## Быстрый старт

```bash
# Веб-камера, метод POS + Welch (по умолчанию)
python scripts/run_webcam.py

# Офлайн-обработка видео с сохранением временного ряда в CSV
python scripts/run_on_video.py --video sample.mp4 --method chrom --freq lomb_scargle --out result.csv

# С конфигом эксперимента и структурированным JSONL-логом по окнам
python scripts/run_on_video.py --video sample.mp4 --config experiment.yaml --out result.csv --log result.jsonl

# Строго причинный режим (как в реальном времени, без второго прохода)
python scripts/run_on_video.py --video sample.mp4 --out result.csv --no-two-pass
```

`--out result.csv` дополнительно сохраняет `result.config.yaml` — точный
конфиг, с которым получен именно этот результат (п.42: "каждая строчка
таблицы в статье должна быть привязана к конкретному конфигу").

Программный API:

```python
from rppg.config import PipelineConfig, ExtractionMethod
from rppg.pipeline import RPPGPipeline
import cv2

config = PipelineConfig(method=ExtractionMethod.POS)
cap = cv2.VideoCapture(0)

with RPPGPipeline(config, log_path="session.jsonl") as pipeline:
    ok, frame = cap.read()
    result = pipeline.process_frame(frame, timestamp_ms=0)
    if result and result.publishable:
        print(result.bpm, result.hrv.sdnn_ms, result.hrv.rmssd_ms)  # валидированное измерение
    elif result:
        print("низкое качество сигнала:", result.warnings)
    if result:
        # ВСЕГДА реальное число — для встраивания как soft-фичи в более
        # крупную систему, которой нужно значение на каждом шаге (см.
        # BestEffortConfig). НЕ валидированное измерение.
        print("auxiliary (always-on):", result.best_effort_bpm)
```

## Валидация и бенчмарки

> **UBFC-rPPG:** изображения лиц `subject21` и `subject27` запрещено публиковать
> (статья, презентация, отчёт) — данные использовать можно, кадры нет.
> Подробности и формат цитирования: [docs/dataset_restrictions.md](docs/dataset_restrictions.md).

### UBFC-rPPG, 50 записей, двухпроходный режим

| метрика | значение |
|---|---|
| **MAE** (усреднение по ИСПЫТУЕМЫМ, не по окнам) | **1.67 ± 0.70 BPM** |
| RMSE | 2.16 ± 1.14 BPM |
| Бутстрэп 95% ДИ среднего MAE (n_boot=10000) | [1.49, 1.87] |
| Покрытие (доля окон с `publishable=True`) | 98.9% |
| Октавные ошибки | 1 окно из 2923 (0.03%) |
| Бланд-Альтман | смещение −0.39 BPM, 95% пределы согласия [−5.76, +4.99] |

**Эталон — ЧСС, вычисленная из формы контактной пульсовой волны, а не
колонка ЧСС прибора.** Авторы датасета пишут в `readme.txt` дословно:
"heart rate values provided by the sensor were not used for evaluating our
heart rate estimation method"; так же поступает rPPG-Toolbox. Только такие
числа сопоставимы с опубликованными на этом датасете. Те же прогоны против
приборной колонки давали MAE 3.56 — разница почти целиком принадлежит
эталону, а не методу: пять записей с систематическим занижением
перестали быть аномалией — их медианное отношение предсказание/эталон
поднялось с 0.90–0.98 до 0.98–1.00, а MAE упало в разы:

| запись | MAE к прибору | MAE к волне | медиана отношения |
|---|---|---|---|
| `subject3` | 9.56 | **2.77** | 0.922 → 0.983 |
| `subject4` | 9.80 | **3.88** | 0.919 → 0.990 |
| `subject14` | 9.31 | **2.32** | 0.977 → 0.998 |
| `subject27` | 7.29 | **3.71** | 0.959 → 0.986 |
| `subject37` | 6.36 | **1.16** | 0.904 → 0.980 |

Всего при смене эталона улучшились 46 записей из 50, ухудшились 4, и все
ухудшения в пределах шума: `subject18` +0.58, `subject11` +0.29,
`subject5` +0.02, `subject48` +0.00 BPM.

Техническая деталь, без которой цифры получаются неверными: в DATASET_2
временная ось контактной волны НЕравномерна (шаг 0.010–0.223 с при медиане
0.040), тогда как метод Уэлча определён только на равномерной сетке. Волна
приводится к равномерной сетке (`np.interp`) перед тем же самым Уэлчем —
именно приведением, а не переходом на Ломба-Скаргла для одного подмножества:
иначе два формата считались бы разными методами и разница между ними
перестала бы что-либо значить.

**Проверка на переобучение.** Разработка велась на 6 записях, остальные 44
не использовались при настройке:

| выборка | n | MAE |
|---|---|---|
| настроечная | 6 | 0.93 ± 0.42 |
| отложенная | 44 | 1.77 ± 0.67 |
| — из них DATASET_1 | 2 | 0.83 |
| — из них DATASET_2 | 42 | 1.82 |

Разрыв настроечная/отложенная (+0.84 BPM) объясняется НЕ подгонкой, а
форматом эталона: настроечные записи — весь DATASET_1 (волна 62.5 Гц,
равномерная), отложенные почти целиком DATASET_2 (волна вдвое-втрое реже,
медианный шаг 0.040 с, и неравномерна). Внутри DATASET_1 отложенные записи (0.83) не хуже
настроечных (0.93). `report_ubfc_split.py` печатает этот контроль на
формат сам, чтобы вывод нельзя было прочитать как «переобучение».

Воспроизведение (одна папка испытуемого за прогон — рассчитано на цикл
«скачал → прогнал → удалил → следующий», строка испытуемого правится на
месте, прежние результаты не теряются):

```bash
PYTHONPATH=src python3 scripts/eval_ubfc_subject.py --subject-dir ~/Downloads/8-gt --two-pass
PYTHONPATH=src python3 scripts/report_ubfc_split.py --results ubfc_results_twopass.csv
PYTHONPATH=src python3 scripts/report_ubfc_split.py --compare   # одно- против двухпроходного
PYTHONPATH=src python3 scripts/analyze_ubfc_windows.py          # SQI-кривая, Бланд-Альтман, MAE по времени и по частоте
```

Результаты накапливаются в `ubfc_results_twopass.csv` (одна строка на
испытуемого), пооконные логи — в `ubfc_windows_twopass/<subject>.csv`,
сводка анализов — в `analysis_ubfc_twopass_wave.txt`. Однопроходные
прогоны пишутся в отдельные `ubfc_results.csv`/`ubfc_windows/`, чтобы обе
методики можно было сравнить, а не подменить одну другой.

Индекс качества на этих данных информативен: при росте порога `sqi_score`
с 0 до 0.9 MAE падает 1.69 → 1.32 (корреляция порога с MAE −0.842), то
есть гейтинг действительно отбрасывает худшие окна, а не случайные.

### Инфраструктура на синтетике

Остальные датасеты (PURE/COHFACE/VIPL-HR/UBFC-Phys) требуют отдельного
Data Use Agreement и не прогонялись. Перечисленное ниже проверено на
синтетических данных с известным BPM:

- `benchmark/evaluate.py` — MAE/RMSE/MAPE/Pearson/CCC/Bland-Altman,
  reference-relative SNR, агрегация ПО ИСПЫТУЕМЫМ с bootstrap CI (не по
  окнам — псевдорепликация, см. докстринги), кривая "покрытие vs ошибка"
  для SQI-гейтинга, стратифицированный анализ.
- `benchmark/skin_tone.py` — объективная ITA-оценка тона кожи для
  стратификации без ручной Fitzpatrick-разметки.
- `scripts/run_ablation_study.py` — полная таблица 6 методов × 3 частотных
  оценки × 3 detrend × 2 режима ROI на синтетике; результат сохраняется в
  `benchmark/ablation_results.csv`.
- `scripts/compare_fusion_vs_argmax.py` — SQI-взвешенный fusion против
  argmax-выбора ROI на синтетике с калиброванным по модальностям шумом.
- `scripts/analyze_tarvainen_lambda.py` — АЧХ detrending-фильтра и
  обоснование выбора λ под fs=30 Гц; график в
  `benchmark/tarvainen_frequency_response.png`.
- `scripts/benchmark_performance.py` — замеры производительности (по
  стадиям, Numba cold/warm, CPU/GPU delegate, сквозной FPS) на конкретном
  железе; результат в `benchmark/performance_report.json`.

## Тесты

```bash
pytest                                   # вся папка tests/, конфиг в pytest.ini
pytest tests/test_signal_pipeline.py -v  # подробный вывод по одному файлу
```

Сигнальный уровень (детрендинг → 6 методов извлечения → 3 метода частотного
анализа → HRV → SQI, включая fusion/harmonic/flicker) проверен на
синтетических, но физиологически правдоподобных данных с известным BPM.
Отдельно — сквозной тест ЧЕРЕЗ `RPPGPipeline.process_frame` целиком (на
кадрах с искусственно пульсирующим цветом "кожи") и негативные контроли
(статичное фото, манекен/шум, белый шум, полностью окклюдированное лицо —
во всех случаях `publishable == False`). MediaPipe и модель в этой среде
доступны — pipeline-уровневые тесты запускают его по-настоящему, но
грациозно пропускаются, если в другой среде их нет.

CI (`.github/workflows/ci.yml`) прогоняет тот же `pytest` на push/PR на
Python 3.9/3.11/3.12.

## Ограничения текущей версии (см. research_report.md за подробностями)

- Валидация на РЕАЛЬНЫХ видео выполнена на одном датасете — UBFC-rPPG (50
  записей). Остальные (VIPL-HR/PURE/MMSE-HR/UBFC-Phys) требуют отдельного
  data use agreement и не прогонялись, поэтому переносимость числа 1.67 BPM
  на другие камеры, освещение и популяции не проверена. UBFC снят в
  контролируемых условиях: сидящий человек, стабильный свет.
- Заявленные 1.67 BPM получены в ДВУХПРОХОДНОМ офлайн-режиме, который в
  реальном времени недоступен по построению (второй проход смотрит на
  историю всей записи). Строго причинный режим — это отдельные
  `ubfc_results.csv`/`ubfc_windows/`, сравнение печатает
  `report_ubfc_split.py --compare`.
- Качество самого эталона у двух форматов UBFC разное (DATASET_1 — волна
  62.5 Гц равномерная, DATASET_2 — ~25 Гц и неравномерная), и часть
  остаточной ошибки принадлежит эталону, а не методу. У `subject20`
  пульсоксиметр частично отказал: с эталоном сверено 38 окон из 58, и MAE
  опирается на урезанную выборку — `report_ubfc_split.py` отмечает такие
  записи знаком `!`. Отдельно от этого у `subject27` самое низкое покрытие
  (72%): там уже SQI не публикует часть окон.
- Результаты SQI-взвешенного fusion и ablation-таблица получены на
  синтетике; величина реального выигрыша (или его отсутствие) на реальных
  видео не подтверждена.
- `--method auto` адаптируется среди КЛАССИЧЕСКИХ методов извлечения (какой
  из GREEN/CHROM/POS/PCA/ICA лучше подходит под текущую камеру) — это не
  преодолевает принципиально недостаточный SNR на входе (слабое/неровное
  освещение, шумная матрица/агрессивное сжатие камеры): если ни один из
  методов не видит пульс в кадре, SQI корректно не публикует результат
  независимо от auto-подбора. Проверено на реальной веб-камере при слабом
  освещении: тон трекинга/детекции лица был идеальным, но spectral SNR не
  поднимался выше −0.6 дБ (нужно ≥3 дБ) — это физическое ограничение
  метода, а не то, что можно исправить исключительно программно.
- HRV-признаки вычисляются из межпульсовых, а не межсердечных (ЭКГ)
  интервалов (PRV, а не HRV в строгом смысле) — см. hrv/features.py, docstring.
- Признаки, полезные для ПТСР-скрининга (HRV/RMSSD/LF-HF), являются
  неспецифичным физиологическим коррелятом, а не диагностическим критерием —
  см. research_report.md, раздел 7.
