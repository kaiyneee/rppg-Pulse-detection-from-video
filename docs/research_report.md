# Research Report: модернизация rPPG-модуля для системы анализа физиологических маркеров ПТСР

**Дата:** июль 2026. **Базовый репозиторий:** [irfan798/head-pulse-track](https://github.com/irfan798/head-pulse-track)
(реализация Balakrishnan, Durand, Guttag, *"Detecting Pulse from Head Motions in Video"*, CVPR 2013).

---

## 0. Резюме

Оригинальный репозиторий — качественная учебная реализация одного конкретного
алгоритма 2013 года, написанная, по признанию автора в README, за 3 дня для
хакатона. Она не использует MediaPipe (в 2019-2020, когда писался код, Face
Mesh только вышел), не имеет ROI кроме "лица за вычетом глаз/рта", реализует
единственный метод извлечения сигнала (motion-based PCA), не измеряет
качество сигнала и не извлекает ничего, кроме мгновенного BPM. Для интеграции
в систему, которая принимает решения о физиологическом состоянии человека,
этого недостаточно ни с инженерной, ни с научной точки зрения.

Ниже: (1) построчный по модулям разбор оригинала, (2) архитектура нового
решения на MediaPipe Face Landmarker + 6 методах rPPG + SQI-гейтингом,
(3) обоснование каждого решения, (4) HRV-признаки и их связь с литературой
по ПТСР, (5) честная граница между инженерным улучшением и научным вкладом,
(6) полный экспериментальный протокол. Код — в `src/rppg/`, протестирован на
синтетических сигналах с известным BPM (см. раздел 8).

## 1. Анализ оригинального репозитория

### 1.1 `main.py`

**Назначение.** CLI-точка входа: парсинг аргументов (`-c` индекс камеры,
`-f` путь к видеофайлу, `--face_detector {haar,dlib,face_shape}`, `--graph`
для визуализации), основной цикл захвата кадров, вызов `FacePoints` →
`TrackPoints` → периодический вызов `SignalProcess`, наложение BPM на кадр.

**Слабые места.**
- Не измеряет реальный FPS камеры — использует номинальное значение. Автор
  сам фиксирует это в TODO README ("for live feed, first get real fps...").
  Это напрямую бьёт по точности: весь частотный анализ ниже (Butterworth,
  FFT) параметризован по `fps`, и если реальный FPS камеры плавает
  (типично для USB-камер при слабом освещении, когда автоэкспозиция
  увеличивает время экспозиции кадра), полосовой фильтр начинает резать не
  ту полосу, а BPM пересчитывается с систематической ошибкой.
- Нет структуры для многокомпонентного экспортируемого результата (BPM в
  файл — тоже открытый пункт TODO в README) — то есть *даже минимальная*
  интеграция с внешней системой не была целью оригинального проекта.
- Монолитный цикл без разделения на "оценка одного окна" / "потоковая
  оркестрация", что затрудняет unit-тестирование (тестов на сигнальную
  математику в проекте нет — есть только `tests/*.ipynb`, т.е. ноутбуки для
  ручного исследования, не автоматические тесты).

**Актуальность на 2026:** архитектурно код 2019-2020 года, до появления
MediaPipe Tasks API, до широкого распространения POS/CHROM в опенсорсе,
без единого формата вывода. Как демонстрация алгоритма статьи 2013 года —
рабочая; как основа production/research-модуля — нет.

### 1.2 `modules/face.py` (`FacePoints`)

**Назначение.** Три взаимозаменяемых детектора лица: Haar-каскад OpenCV,
детектор лица Dlib (HOG+SVM), Dlib 68-точечный landmark-предиктор
(`shape_predictor_68_face_landmarks.dat`). Для первых двух — после
нахождения прямоугольника лица вручную вычитается область глаз (эвристика
по геометрии прямоугольника), чтобы моргание не загрязняло сигнал движения.

**Алгоритм.** Haar/Dlib: детекция прямоугольника → геометрическая маска
"минус глаза" → `cv2.goodFeaturesToTrack` (Shi-Tomasi) внутри маски для
получения точек. Face_shape: полный 68-точечный Dlib-ландмарк, из которого
исключаются точки глаз и рта.

**Слабые места.**
- Haar-каскад — детектор 2001 года (Viola-Jones), не даёт landmark'ов, а
  только прямоугольник; чувствителен к повороту головы и освещению.
- Dlib 68-точечный предиктор (2014, One Millisecond Face Alignment)
  устойчивее, но заметно медленнее современных мобильных моделей и не
  даёт 3D/позы головы напрямую.
- "Минус глаза/рот" — geometric-эвристика на прямоугольнике, а не
  анатомически осмысленная маска региона (лоб/щёки как таковые не
  выделяются нигде, вопреки тому, что просит ТЗ этого проекта).
- Ни один из трёх режимов не даёт confidence/presence score для кадра →
  невозможно понять, "поймал" ли детектор лицо уверенно или на грани.

**Актуальность на 2026 (проверено эмпирически, не "по памяти"):** в
установленной для разработки этого отчёта версии `mediapipe==0.10.33` при
попытке `import mediapipe.solutions` или `mediapipe.python.solutions`
получена `ModuleNotFoundError` — legacy Solutions API (в т.ч. классический
`mp.solutions.face_mesh`, на который чаще всего ссылаются старые
рекомендации "просто замените Haar на MediaPipe") физически отсутствует в
пакете. Единственный работающий путь — `mediapipe.tasks.python.vision.
FaceLandmarker` (Tasks API). Это значит: подход `face.py` устарел не
"стилистически", а в смысле "не собрать эквивалент на актуальном пакете
без миграции на новый API" — что и сделано в `src/rppg/face/landmarker.py`.

### 1.3 `modules/tracking.py` (`TrackPoints`)

**Назначение.** Покадровое сопровождение точек методом Лукаса-Канаде
(`cv2.calcOpticalFlowPyrLK`), с проверкой forward-backward консистентности
(трекинг вперёд, затем назад; если точка не возвращается близко к исходной
позиции — трасса помечается "faulty" и удаляется). Для Haar/Dlib-режима
недостающие точки перезапрашиваются у `FacePoints` до `max_trace_num`
(по умолчанию 150). Для face_shape — переотслеживаются именно 68
ландмарков, "плохие" точки точечно заменяются.

**Слабые места.**
- KLT — покадровый метод без модели лица; при быстром повороте головы или
  частичной окклюзии (рука, волосы, маска) трассы массово "теряются"
  одновременно, и переинициализация недёшева.
- Forward-backward проверка — качественная эвристика, но она детектирует
  только *потерю* трекинга, а не *низкое качество* всё ещё "живой" точки
  (например, точка съехала на бровь вместо кожи — трекинг не потерян, но
  сигнал больше не годится для rPPG).
- Нет учёта позы головы (yaw/pitch/roll) как таковой — только 2D-смещение
  точек, что подходит для алгоритма головного движения (это и есть его
  физическая основа), но не даёт независимого сигнала "насколько сильно
  повёрнута голова" для гейтинга качества по ROI.

**Актуальность на 2026:** сам KLT — валидный, до сих пор используемый
алгоритм (входит в OpenCV), но здесь он тянет на себе задачи, которые
современный face-landmark трекер (со встроенным temporal tracking внутри
модели, как в MediaPipe Tasks VIDEO running mode) решает надёжнее и с
готовой оценкой уверенности по каждому кадру.

### 1.4 `modules/signal_processing.py` (`SignalProcess`)

**Назначение и алгоритм.** Берёт Y-компоненту (вертикальное смещение)
отслеженных трасс → 5-й порядок Butterworth bandpass [0.75, 3] Hz (45–180
BPM) → для Haar/Dlib: PCA до 5 компонент, для каждой — доминирующая частота
через FFT, отбор компоненты с максимальной долей спектральной мощности,
сосредоточенной вокруг её пика ("наиболее периодичная" компонента — прямая
реализация критерия отбора из статьи Balakrishnan et al.); для face_shape:
упрощённо — среднее по трассам → FFT на среднем сигнале (без PCA).

**Слабые места.**
- Единственный источник сигнала — движение. Нет цветового (истинно
  фотоплетизмографического) канала вообще: ни GREEN, ни CHROM, ни POS.
  Между тем в независимых сравнениях (см. раздел 3.4 и rPPG-Toolbox,
  Liu et al., NeurIPS 2023) цветовые методы, особенно POS, как правило
  дают более низкую ошибку и лучшую устойчивость к умеренному движению,
  чем чисто motion-based подход — то есть репозиторий реализует не
  "средний", а один из наименее устойчивых к движению вариантов, для
  системы, которая как раз обязана быть устойчивой к движению головы.
- Только FFT для оценки частоты — самый шумный из трёх статистически
  стандартных вариантов (нет усреднения сегментов, как в Welch; не
  определён на нерегулярной сетке, как Lomb-Scargle).
- Полоса 45–180 BPM — уже, чем физиологически стоит закладывать для
  системы, которая потенциально увидит острую стрессовую реакцию
  (тахикардия существенно выше 180 уд/мин у части людей при остром
  стрессе — редко, но полоса должна иметь запас, а не отрезать такие
  случаи по построению).
- Нет никакой количественной оценки качества сигнала — BPM выводится
  всегда, независимо от того, насколько сигнал зашумлён. Для
  ПТСР-интеграции это прямой риск: недостоверное число неотличимо от
  достоверного на выходе.
- Нет HRV вообще — только мгновенный BPM. Между тем в аннотации самой
  статьи Balakrishnan et al. авторы также сообщают о получении клинически
  релевантной информации об изменчивости сердечного ритма — то есть даже
  оригинальный алгоритм 2013 года *потенциально* способен на это, но в
  данной реализации это не использовано.

**Актуальность на 2026:** ядро (PCA + критерий периодичности) методологически
не устарело как идея — оно переиспользовано и в новой архитектуре (см.
`HeadMotionMethod`, `select_best_component_by_periodicity`), но как
единственный метод извлечения сигнала, без цветовых альтернатив,
частотного усреднения и SQI — недостаточно для 2026 года.

### 1.5 `data/` (Haar-каскады, `shape_predictor_68_face_landmarks.dat`)

Статические веса моделей 2001/2014 годов. Устарели по точности и скорости
относительно современных мобильных detection+landmark моделей (MediaPipe

на порядок компактнее и точнее по геометрии, особенно в 3D).

## 3. Архитектура нового решения

### 3.1 Детекция лица: Face Mesh vs Face Landmarker

| | MediaPipe **Face Mesh** (legacy Solutions API) | MediaPipe **Face Landmarker** (Tasks API) |
|---|---|---|
| Статус в 2026 | Физически недоступен в `mediapipe>=0.10.x` — проверено импортом в этой среде (`ModuleNotFoundError`) | Актуальный, поддерживаемый путь |
| Landmarks | 468 точек | 468 точек (то же геометрическое ядро) |
| Поза головы | Нет напрямую (нужен отдельный solvePnP) | `facial_transformation_matrixes` — готовая 4×4 матрица позы |
| Мимика/blendshapes | Нет | 52 ARKit-подобных коэффициента (`output_face_blendshapes`) |
| Режимы работы | Только потоковый, неявный | `IMAGE` / `VIDEO` / `LIVE_STREAM`, явные, с `min_tracking_confidence` |
| Делегат CPU/GPU | Ограниченно | Явный параметр `BaseOptions.Delegate` |

**Выбор: Face Landmarker (Tasks API).** Не только из-за дополнительных
полей, а потому что альтернативы у актуального пакета MediaPipe уже нет.
Дополнительный практический бонус: `facial_transformation_matrixes` напрямую
даёт yaw/pitch/roll (реализовано в `face/landmarker.py::_rotation_matrix_to_euler_deg`)
— это самостоятельный, независимый от ROI-сигнала индикатор движения
головы, который используется в SQI (§3.4) для гейтинга по устойчивости к
движению — то, чего в оригинале не было вообще.

**Модель.** Файл `.task` не входит в pip-пакет (в отличие от старого Solutions
API, где веса были зашиты в пакет) и должен быть скачан один раз:
```
https://storage.googleapis.com/mediapipe-models/face_landmarker/face_landmarker/float16/latest/face_landmarker.task
```
Для воспроизводимости эксперимента рекомендуется зафиксировать версию
(`float16/1/...`) вместо `latest`, иначе Google может обновить веса модели
между экспериментами без явного уведомления, и результат перестанет быть
строго воспроизводимым.

### 3.2 Динамический ROI: лоб, левая/правая щека

Индексы landmark-точек **не взяты "по памяти"**, а извлечены
программным интроспектированием установленного пакета (`mediapipe.tasks.
python.vision.face_landmarker.FaceLandmarksConnections`) — см. полный
список опорных множеств (`FACE_OVAL`, `LEFT/RIGHT_EYE`, `LEFT/RIGHT_EYEBROW`,
`NOSE`, `LIPS`) и построенные из них полигоны ROI в `face/roi.py`. Это
принципиальное методологическое решение: неверные индексы — тихая, трудно
диагностируемая ошибка (ROI "почти правильный", результат правдоподобно
неверный), поэтому для итоговых полигонов взяты **только** индексы,
подтверждённые прямым запросом к библиотеке, а не эвристически
восстановленные по картинкам топологии из интернета.

Геометрия (см. докстринг `face/roi.py` для точных индексов):
- **Лоб** — между верхними точками бровей и верхней частью овала лица
  у висков (MediaPipe не размечает линию роста волос напрямую — овал лица
  как разумная верхняя граница).
- **Щёки** — между нижним веком, крылом носа, углом рта и внешним краем
  овала (скуловая область — стандартный ROI в rPPG-литературе, зона с
  хорошей перфузией, минимально задействованная в мимике по сравнению с
  областью рта).

Каждый полигон дополнительно **сжимается к центроиду** (`shrink_factor`,
по умолчанию 0.9) — снижает риск захвата фона/волос/ушей на границе при
повороте головы, и **гейтится по яркости** (`roi_mean_rgb`) — пиксели с
клиппингом (пере-/недоэкспонирование) исключаются из усреднения, а кадр
целиком помечается невалидным, если таких пикселей больше 40% ROI (пункт
"устойчивость к освещению" ТЗ).

### 3.3 Поток данных пайплайна

```
Кадр (BGR)
   │
   ▼
FaceLandmarkerWrapper.detect()  ──▶  468 landmarks + поза головы (yaw/pitch/roll)
   │
   ▼
roi.extract_rois()  ──▶  {forehead, left_cheek, right_cheek}: mean RGB (или "невалидно")
   │
   ▼
Кольцевой буфер (скользящее окно, WindowConfig)
   │  interpolate_missing() — короткие провалы интерполируются,
   │  длинные помечают ROI невалидным на всё окно
   ▼
Для каждого валидного ROI:
   PulseExtractionMethod.extract()  [GREEN|CHROM|POS|PCA|ICA|HEAD_MOTION]
   preprocess_signal()  [detrend → normalize → bandpass]
   estimate_hr()  [FFT|Welch|Lomb-Scargle]
   │
   ▼
assess_quality()  ──▶  SQI (спектральный SNR + межзонное согласие + стабильность landmark)
   │
   ├── SQI < порога ──▶  publishable=False, BPM/HRV НЕ уходят в ПТСР-систему, warnings
   │
   ▼ SQI ≥ порога
extract_hrv_features()  ──▶  Mean HR, SDNN, RMSSD, pNN50, pNN20, LF/HF
   │
   ▼
PTSDPulseFeatures  ──▶  потребитель (система анализа ПТСР)
```

### 3.4 Архитектурные паттерны

- **Strategy** для методов извлечения сигнала (`PulseExtractionMethod` +
  `METHOD_REGISTRY`) и для частотного анализа (`ESTIMATORS`) — переключение
  без изменения остального кода, прямая реализация требования ТЗ
  "реализовать несколько методов и сделать переключение между ними".
- **Явная конфигурация как данные**, не константы в теле функций
  (`config.py`, датаклассы) — обязательное условие воспроизводимости
  эксперимента; в оригинале параметры (полоса фильтра, число PCA-компонент,
  `max_trace_num`) разбросаны по коду.
- **Fail-soft, не fail-hard**: ошибка в одном ROI/методе (`FastICA` не
  сошёлся, окно слишком короткое для `filtfilt`) не роняет пайплайн, а
  деградирует до безопасного поведения с warning — важно для системы,
  которая должна работать непрерывно на потоке, а не падать на первом
  сложном кадре.

## 4. Обоснование ключевых решений

### 4.1 Шесть методов извлечения сигнала: сравнение

| Метод | Источник сигнала | Идея | Сильные стороны | Слабые стороны |
|---|---|---|---|---|
| **GREEN** | цвет | зелёный канал наиболее чувствителен к объёмному пульсу (Verkruysse et al., 2008) | простота, baseline | нет устойчивости к движению/освещению |
| **CHROM** | цвет | хроминантная комбинация, ортогональная тону кожи (de Haan & Jeanne, 2013) | устойчивее к умеренному движению, чем GREEN | требует относительно стабильного освещения в пределах окна |
| **POS** | цвет | скользящее окно + проекция на плоскость, ортогональную направлению кожи (Wang et al., 2016) | в независимых бенчмарках обычно лучший/наравне с лучшими среди классических методов | чуть выше вычислительная стоимость (компенсируется Numba, см. §6) |
| **PCA (цвет)** | цвет | ортогональное разложение нормализованных каналов + выбор по периодичности (Lewandowska et al., 2011) | не требует знания направления "кожного" сигнала | ортогональность ≠ независимость источников — слабее ICA при сильно коррелированных артефактах |
| **ICA (цвет)** | цвет | независимые компоненты вместо ортогональных (Poh, McDuff, Picard, 2010/2011) | теоретически лучше разделяет источники разной статистической природы | недетерминированность инициализации, риск несходимости на коротких/шумных окнах (обработано fallback на PCA) |
| **Head-motion** | движение | баллистокардиографический отклик головы (Balakrishnan et al., 2013) | не требует хорошего цветового сигнала (работает в ИК/ч/б, при плохом цветовоспроизведении камеры) | чувствителен к произвольным (не сердечным) движениям головы |

Почему POS — метод по умолчанию (`config.PipelineConfig.method`): в
сравнительном анализе самой статьи POS (Wang et al., 2016) и в
последующей независимой инфраструктуре сравнения rPPG-методов
(**rPPG-Toolbox**, Liu et al., NeurIPS 2023 Datasets & Benchmarks track,
реализующей унифицированное сравнение ICA/CHROM/LGI/PBV/POS/OMIT и рядом
DL-методов на общих датасетах) POS стабильно входит в число лучших
классических unsupervised-методов по MAE/RMSE на стандартных бенчмарках.
Наличие всех шести методов и Strategy-паттерна означает, что выбор метода
по умолчанию — не догма: конкретный сценарий (например, инфракрасная
камера ночного видения без цветового канала) может обосновать переключение
на `HEAD_MOTION`, а при экстремально коротких окнах — на `GREEN`/`CHROM`
как наиболее дёшево вычисляемые.

### 4.2 Подавление шума

- **Tarvainen smoothness-priors detrending** (по умолчанию) вместо
  наивного линейного — снимает нелинейный дрейф (дыхание, плавное
  изменение освещения, медленное сползание ROI при повороте головы) без
  необходимости заранее знать его форму; параметр `λ` задаёт "жёсткость"
  того, что считается трендом. Линейный detrend оставлен как быстрый
  fallback-режим.
- **Z-score нормализация** — обязательна перед CHROM/POS/PCA/ICA: все они
  комбинируют каналы линейно, и если каналы находятся в разных масштабах,
  комбинация будет доминироваться каналом с большей дисперсией по
  случайной, а не физиологической причине.
- **Butterworth bandpass, zero-phase (`filtfilt`)**, а не `lfilter` —
  принципиально для HRV: обычная (не zero-phase) фильтрация вносит
  частотно-зависимую фазовую задержку, которая искажает точное время
  пиков пульсовой волны, а вся идея HRV/RMSSD/SDNN держится именно на
  точном времени пиков. Butterworth выбран (а не Чебышев/эллиптический)
  из-за максимально плоской АЧХ в полосе пропускания — без пульсаций,
  которые исказили бы форму пульсовой волны.
- **Motion artifact removal** реализован на двух уровнях: (а) пиксельный
  гейтинг ROI по яркости/валидности перед агрегацией в трейс, (б)
  `interpolate_missing` — линейная интерполяция коротких провалов
  (потеря трекинга на несколько кадров) с жёсткой границей `max_gap`,
  после которой окно вместо "подлечивания" честно помечается невалидным.

### 4.3 Частотный анализ: почему Welch — метод по умолчанию, а Lomb-Scargle — не опциональная роскошь

FFT на целом окне (то, что использовал оригинал) — несмещённая, но
высокодисперсная оценка спектра при коротких зашумлённых окнах: один
случайный выброс может сдвинуть положение пика. Welch снижает дисперсию
усреднением по перекрывающимся сегментам ценой частотного разрешения,
которое здесь компенсируется zero-padding (`nfft`, отвязанный от `nperseg`
— см. `signal/frequency.py`) для точной локализации пика без потери
статистической устойчивости усреднения.

Lomb-Scargle — не "третий вариант на всякий случай", а единственный из
трёх, формально корректный на **неравномерной по времени** сетке. После
исключения кадров с окклюзией/потерей трекинга (§4.2) валидные отсчёты
сигнала располагаются неравномерно во времени; FFT/Welch формально
предполагают равномерную дискретизацию и *требуют* предварительной
интерполяции на равномерную сетку, что само по себе — источник
дополнительных артефактов на границах пропусков. Lomb-Scargle работает
напрямую с исходными временными метками. Это протестировано явно
(`tests/test_signal_pipeline.py::test_lombscargle_handles_irregular_sampling`)
на сигнале с ~15% случайно "окклюдированных" отсчётов.

### 4.4 Signal Quality Index и гейтинг

Три независимых компоненты (детали и веса — `signal/quality.py`):
1. **Спектральный SNR** — насколько энергия сосредоточена вокруг
   предполагаемой частоты пульса, а не размазана по полосе (мера
   "пульсоподобности" самого сигнала).
2. **Межзонное согласие** — оценки BPM с лба и с двух щёк должны сходиться;
   расхождение обычно означает, что один ROI зашумлён локально (тень,
   блик, окклюзия), а не что метод в целом сломан — это прямое следствие
   того, что ROI три, а не один, и позволяет отличить "плохой один датчик"
   от "плохой сигнал в принципе".
3. **Стабильность landmark-точек** — покадровое дрожание стабильного
   набора точек лица (`STABLE_TRACKING_IDX`) как proxy устойчивости
   трекинга/наличия резких движений или окклюзии.

Если итоговый `overall_score` ниже порога — `PTSDPulseFeatures.publishable
= False`. Это единственное место, где реализовано жёсткое требование ТЗ
"не передавать значение BPM в систему ПТСР [при низком качестве]": интеграция
обязана проверять именно этот флаг, а не наличие числа в поле `bpm` (оно
всегда присутствует для отладки/логирования, но не должно интерпретироваться
потребителем как достоверное при `publishable=False`).

## 5. HRV-признаки и их связь с ПТСР

### 5.1 Реализованные признаки (`hrv/features.py`)

Mean HR, SDNN, RMSSD, pNN50 (обязательные по ТЗ) + pNN20, mean IBI, CV IBI,
LF power, HF power, LF/HF ratio (частотный HRV, бонус) + Pulse Signal
Quality Score (перенос итогового SQI на уровень признаков, чтобы
потребитель мог принять решение о доверии к конкретному значению HRV
независимо от решения о доверии к BPM).

### 5.2 Почему именно эти признаки релевантны для ПТСР — с опорой на литературу

- **Мета-анализ Schneider & Schwerdtfeger (2020, *Psychological Medicine*)**,
  посвящённый автономной дисрегуляции при ПТСР, зафиксировал устойчивые
  групповые различия: сниженные RMSSD и HF-HRV (маркеры вагусной/
  парасимпатической активности) у людей с ПТСР по сравнению с контролем,
  умеренный эффект по SDNN (сниженная общая вариабельность), более высокое
  отношение LF/HF (сдвиг баланса в сторону симпатической активности) и
  повышенная ЧСС в покое; при стресс-пробах — дополнительное повышение ЧСС
  и дальнейшее снижение HF-HRV в группе ПТСР.
- **Мета-анализ 2026 года по вагус-опосредованной ВСР (vmHRV) при ПТСР**
  (24 исследования, 2537 участников, 34 эффекта) независимо подтверждает
  устойчиво сниженную vmHRV у людей с ПТСР, с указанием на то, что
  величина эффекта зависит от методологии (в т.ч. длительности записи) —
  что напрямую релевантно выбору `window_seconds` в `WindowConfig` и
  мотивирует протокол §9 отдельно тестировать чувствительность к длине окна.

Иными словами: RMSSD/HF (через LF/HF) и SDNN — не произвольный список "раз
уж мы умеем считать HRV", а именно те показатели, для которых в литературе
по ПТСР накоплена наиболее устойчивая доказательная база.

### 5.3 Методологическая оговорка: PRV ≠ HRV

Показатели вычисляются из межпульсовых интервалов **PPG**-сигнала (Pulse
Rate Variability, PRV), а не из R-R интервалов ЭКГ (классическая HRV).
Обзор **Schäfer & Vagedes (2013, *International Journal of Cardiology*)**
показывает, что PRV — хорошая, но не идентичная аппроксимация ЭКГ-HRV:
согласие высокое у здоровых людей в покое, но ухудшается при движении и
сосудистых изменениях. Для rPPG (PRV, дважды производной величины — сначала
PPG вместо ЭКГ, затем оценённой дистанционно вместо контактного датчика)
эта оговорка ещё важнее. **Вывод для публикации:** в статье необходимо
явно указывать "rPPG-derived PRV" вместо "HRV" везде, где не проведена
прямая валидация против синхронной ЭКГ, и включить такую валидацию в
экспериментальный протокол (см. §9.3).

### 5.4 Этические и регуляторные аспекты (относится к научной новизне и экспериментам, не к текущему коду)

Cоздание системы, оценивающей физиологические корреляты психиатрического
состояния по видео лица, требует (независимо от точности алгоритма самого
по себе):
- информированного согласия участников на сбор видео и производных
  физиологических показателей;
- одобрения этического комитета (IRB) для любого сбора данных с людьми,
  особенно с клинической выборкой (ПТСР);
- валидации не только точности BPM/HRV, но и итоговой связи с ПТСР —
  против признанных клинических инструментов (например, CAPS-5 как
  структурированное клиническое интервью, PCL-5 как самоотчёт), а не
  использования HRV как самостоятельного диагностического критерия;
- explicit framing результата как *неспецифичного физиологического
  коррелята* в мультимодальной системе (наряду с речью, поведенческими,
  self-report признаками), а не как автономного диагностического теста —
  HRV снижается при ПТСР, но также при тревожности, депрессии, плохом сне,
  детренированности, приёме ряда препаратов и просто остром стрессе любой
  природы; специфичность умеренная даже при статистически значимой связи
  на уровне групп.
- отдельного внимания к смещению (bias) точности rPPG по тону кожи:
  известная проблема оптических PPG/rPPG-методов (различия в поглощении
  света меланином влияют на амплитуду AC-компоненты сигнала) — протокол
  §9.3 явно включает разбивку точности по группам тона кожи, а не только
  общий MAE по датасету.

## 6. Производительность: Python 3.12 / OpenCV / MediaPipe / NumPy / SciPy + Numba / PyTorch / ONNX

Весь код разработан и протестирован под **Python 3.12.3**, `numpy 2.4.4`,
`scipy 1.17.1`, `opencv-python 4.13.0`, `mediapipe 0.10.33`, `scikit-learn
1.8.0` (точные версии — `requirements.txt`).

**Где реально стоит ускорение, а где нет — предметно, а не "для галочки":**

- **MediaPipe-инференс** — уже скомпилированный TFLite-граф
  (XNNPACK/GPU-делегат). Ни Numba, ни ручной PyTorch/ONNX здесь не
  ускорят сам инференс; единственный реальный рычаг — параметр
  `delegate='GPU'` в `FaceModelConfig`, если целевая платформа его
  поддерживает.
- **Усреднение пикселей по ROI-маске** (`cv2.fillConvexPoly` + `np.mean`
  по маске) — уже C-векторизовано в OpenCV/NumPy; Numba здесь не даёт
  выигрыша, сопоставимого с накладными расходами JIT-компиляции.
- **CHROM/GREEN/PCA/ICA** — работают на векторах из нескольких сотен
  отсчётов (типичное окно 10 с × 30 fps = 300 точек); тот же аргумент.
- **POS со скользящим окном (overlap-add)** — единственное место с явным
  Python-циклом по кадрам (не тривиально векторизуется без потери
  читаемости): на 10-секундном окне при 30 fps это ~250-270 итераций
  внутреннего цикла *на каждый* шаг пайплайна (обновление раз в
  `step_seconds`). Здесь `@numba.njit` даёт измеримое ускорение —
  реализовано в `accel/fast_ops.py`, **корректность проверена**: результат
  numba-ветки побайтово (до `1e-16`) совпадает с эталонной numpy-версией
  на контрольном сигнале (см. раздел 8).
- **PyTorch** в базовом пайплайне не используется вообще — он не нужен
  классическим методам. Его естественное место — если/когда в
  `METHOD_REGISTRY` добавляется **обучаемый** метод извлечения сигнала
  (deep rPPG, см. §10): PyTorch — для обучения/экспериментов, а не для
  инференса в проде.
- **ONNX Runtime** (уже присутствует и протестирован в среде разработки:
  `onnxruntime 1.24.4`) — естественный путь **деплоя** такого обучаемого
  метода: экспорт из PyTorch в `.onnx`, инференс через `onnxruntime`
  без зависимости от PyTorch в проде. В `config.AccelerationConfig`
  заложены поля `use_onnx_for_learned_method` / `onnx_model_path`
  именно под этот сценарий — оба сейчас `False`/`None`, потому что
  обучаемого метода в базовой поставке нет (см. честное разграничение
  в §7 и §10).

## 7. Научная новизна: что инженерное улучшение, а что — потенциальный вклад в статью

**Прямо инженерное (модернизация, не новизна как таковая):**
- Миграция Haar/Dlib → MediaPipe Face Landmarker.
- Замена единственного motion-based метода на набор из 6 сравниваемых
  методов извлечения с переключением.
- SQI/гейтинг, HRV-модуль, Numba-ускорение, тестовое покрытие,
  реорганизация в пакет с явной конфигурацией.

Всё это важно и обязательно для того, чтобы систему вообще можно было
использовать в исследовании, но само по себе не публикуется как научный
результат — это доведение существующих, известных по отдельности техник
до состояния работающей интегрированной системы.

**Потенциально публикуемый вклад (требует экспериментальной проверки,
см. §9, и честно не может быть заявлен без неё):**
1. **Мультизонный (лоб + 2 щеки) SQI на основе межзонного согласия** как
   самостоятельный, недорогой сигнал качества — если экспериментально
   показать, что он ловит случаи низкого качества, пропускаемые
   одноканальными SQI-метриками (например, локальная тень на одной щеке
   при в остальном хорошем сигнале), это методологический вклад, а не
   просто инженерная удобная штука.
2. **Систематическое сравнение 6 методов извлечения именно в контексте
   последующей HRV-оценки** (не только точности BPM) — большинство
   опубликованных сравнений (включая POS/CHROM оригинальные статьи и
   rPPG-Toolbox) оптимизированы и валидированы по точности **BPM**;
   вопрос "какой классический метод даёт наиболее достоверный RMSSD/SDNN",
   то есть сохраняет точное **время** пиков, а не только их частоту —
   исследован в литературе заметно меньше и является конкретным,
   проверяемым вкладом при должном экспериментальном протоколе (§9.3,
   валидация против синхронной ЭКГ).
3. **Специфичность физиологических коррелятов ПТСР при бесконтактном (а
   не контактном) измерении** — сама связь HRV/ПТСР установлена на
   ЭКГ/контактном PPG (§5.2); систематическая проверка, сохраняется ли
   она (и с каким затуханием точности) при переходе на rPPG — открытый,
   недостаточно изученный вопрос, прямая новизна при условии клинической
   валидации (не только технической).
4. **Публичный, воспроизводимый пайплайн с фиксированной версией модели
   и явной конфигурацией** — учитывая, что многие rPPG-репозитории
   (включая исходный) не фиксируют версии моделей/параметры полностью,
   вклад в воспроизводимость сам по себе имеет ценность (особенно для
   систематических обзоров и мета-анализов, как в §5.2, где качество
   мета-анализа явно ограничено методологической неоднородностью
   первичных исследований).

Пункты 1–3 **не могут** быть заявлены как результат до прогона
экспериментального протокола ниже — на синтетике (раздел 8) проверена
только корректность реализации, не превосходство над альтернативами на
реальных данных.

## 8. Валидация, проведённая в рамках этой работы

### 8.1 Что протестировано и как (полностью воспроизводимо, без сети/MediaPipe)

`tests/test_signal_pipeline.py` — 7 тестов на синтетических, но
физиологически правдоподобных сигналах (амплитуда пульсовой AC-компоненты
~1% DC, разные коэффициенты усиления по каналам R/G/B, форма волны — сумма
двух гармоник, а не идеальная синусоида):

| Тест | Результат в этой среде |
|---|---|
| GREEN/CHROM/POS/PCA/ICA восстанавливают известный BPM (72.0) | ошибка 0.07–3.5 BPM (в пределах допуска) |
| HEAD_MOTION восстанавливает известный BPM (68.0) по синтетическим траекториям | ошибка 0.32 BPM |
| FFT/Welch/Lomb-Scargle согласованы на чистом тоне (90.0) | ошибка 0.05–0.35 BPM |
| Lomb-Scargle корректен при ~15% случайно исключённых отсчётов | ошибка 0.06 BPM |
| Butterworth bandpass подавляет внеполосный дрейф | мощность в полосе на порядок выше, чем у 0 Hz |
| Tarvainen/linear detrend устраняют квадратичный тренд | edge-to-edge разница снижена на два порядка |
| HRV-признаки совпадают с аналитически заданной статистикой IBI | Mean HR и SDNN в пределах ожидаемого допуска |

Отдельно проверена побитовая эквивалентность Numba-ветки POS и эталонной
numpy-реализации (разница `4.4e-16`, машинная точность) — важно, поскольку
в среде разработки этого отчёта Numba физически не установлена (нет сети
для `pip install`), и без этой проверки корректность ускоренного пути
осталась бы недоказанной.

Метрики `benchmark/evaluate.py` (MAE/RMSE/MAPE/Pearson/Bland-Altman)
проверены doctest'ами на контрольных числах и дополнительно на
контролируемой синтетике (заданное смещение +1.5 BPM и SD=3 BPM
корректно восстанавливаются как bias и ширина Bland-Altman LoA).

### 8.2 Что осознанно НЕ протестировано в этой среде — и почему

- **Реальное видео/веб-камера.** В среде разработки нет доступа к камере.
- **Модель MediaPipe Face Landmarker.** Файл `.task` не входит в pip-пакет
  и требует сетевого скачивания; сеть в этой среде отключена для
  bash-инструмента. Корректность API-вызовов (`BaseOptions`,
  `FaceLandmarkerOptions`, `FaceLandmarker.detect_for_video`, поля
  результата) проверена не запуском на реальном изображении, а прямой
  интроспекцией установленного пакета (сигнатуры, поля датаклассов) —
  см. §3.1 и докстринги `face/landmarker.py`. Индексы точек ROI (§3.2)
  верифицированы тем же способом. Перед реальным использованием
  рекомендуется прогнать `scripts/run_webcam.py` на живом видео.
- **Реальные датасеты (VIPL-HR/UBFC-rPPG/PURE/MMSE-HR).** Распространяются
  по data use agreement, весят от сотен MB до десятков GB — недоступны без
  сети. `benchmark/evaluate.py` реализует полный интерфейс оценки и
  конкретный загрузчик под формат UBFC-rPPG, но никаких MAE/RMSE-чисел по
  этим датасетам в этом отчёте не приводится — это были бы придуманные
  цифры, что неприемлемо для научного отчёта. Раздел 9 — протокол,
  который нужно прогнать самостоятельно после получения доступа к данным.
- **Numba/PyTorch в реальном исполнении** — пакеты не установлены в этой
  среде (нет сети для установки); корректность логики Numba-ветки
  проверена запуском той же функции без JIT-компиляции (см. 8.1), что
  проверяет правильность алгоритма, но не сам факт ускорения на реальном
  железе — цифры "10-30×", упомянутые в `accel/fast_ops.py`, — это
  типичный порядок ускорения для аналогичных числовых циклов по опыту
  сообщества Numba, а не результат измерения на этом коде; это тоже
  предстоит измерить на целевом железе перед тем, как приводить точные
  цифры в статье.

## 9. Экспериментальный протокол для публикации

### 9.1 Датасеты

| Датасет | Особенности | Что проверяем |
|---|---|---|
| **UBFC-rPPG** (Bobbia et al., 2019) | Небольшой (42 субъекта, DATASET_2), контролируемое освещение, минимум движения | Базовая точность методов в "лёгких" условиях; сюда уже есть готовый загрузчик (`benchmark/evaluate.py::UBFCrPPGLoader`) |
| **PURE** (Stricker et al., 2014) | 10 субъектов × 6 сценариев движения головы (стабильно/разговор/медленное-быстрое вращение/маленькое-большое вращение) | Целевой тест на "устойчивость к движению головы" — прямое требование ТЗ |
| **VIPL-HR** (Niu et al., 2018/2019) | ~2000 видео, 107 субъектов, 9 сценариев (движение, освещение, разговор), несколько устройств записи, разнообразие по демографии | Кросс-девайсовая генерализация + разбивка по условиям освещения/тону кожи (§5.4) |
| **MMSE-HR** (Zhang et al., 2016) | Синхронизировано с индуцированными эмоциональными реакциями (elicited expressions) | Ближайший по духу к сценарию ПТСР-системы прокси-датасет: пульс в условиях выраженной, не нейтральной мимики/аффекта — тест на устойчивость ROI к мимике, не только к вращению головы |

### 9.2 Метрики (реализованы и протестированы в `benchmark/evaluate.py`)

Per-window/per-video: **MAE (BPM)**, **RMSE (BPM)**, **MAPE (%)**,
**Pearson r** (между временным рядом rPPG-BPM и референсным ЭКГ/PPG-BPM),
**Bland-Altman** (bias + 95% limits of agreement; отдельно — проверка,
расширяется ли разброс ошибки на высоких значениях ЧСС, что напрямую
касается достоверности при стрессовой тахикардии). Дополнительно для
HRV-признаков (там, где у датасета есть синхронный ЭКГ, напр. MMSE-HR/
частично VIPL-HR): те же метрики отдельно для SDNN/RMSSD, а не только для
BPM — по причине, изложенной в §7, пункт 2.

### 9.3 Дизайн эксперимента

1. **Основной бенчмарк** — по каждому датасету, по каждому из 6 методов
   извлечения × по каждому из 3 методов частотного анализа (18 комбинаций)
   — таблица MAE/RMSE/Pearson, чтобы обосновать выбор POS+Welch по
   умолчанию эмпирически, а не только по литературным данным (§4.1).
2. **Ablation SQI** — сравнить точность на подвыборке "высокий SQI" против
   "низкий SQI, не отфильтровано" — количественно показать, что гейтинг
   действительно отсекает недостоверные оценки, а не режет случайно.
3. **Устойчивость к движению головы** — на PURE, по сценариям движения:
   точность каждого метода как функция амплитуды движения (из
   `facial_transformation_matrixes`) — прямая проверка требования ТЗ.
4. **Устойчивость к освещению** — на VIPL-HR (есть сценарии с
   контролируемым изменением освещения): точность как функция доли
   гейтированных (клиппинг) пикселей ROI.
5. **Устойчивость к частичной окклюзии** — синтетическая окклюзия (маска
   рукой/маской, программно наложенная на видео из UBFC-rPPG/PURE) как
   контролируемый прокси-эксперимент, плюс, если доступно, естественные
   окклюзии в VIPL-HR.
6. **Разбивка по тону кожи** (Fitzpatrick-подобная категоризация, где
   доступна демографическая аннотация, иначе — оценка по доминирующему
   тону ROI как приближение) — обязательный срез, а не опциональный,
   учитывая известную предвзятость PPG-технологий (§5.4).
7. **Кросс-датасетная генерализация**: обучение/калибровка порогов SQI на
   одном датасете, проверка на других без повторной калибровки —
   особенно важно, если в будущем в `METHOD_REGISTRY` добавляется
   обучаемый метод (§10), для которого переобучение под каждый датасет
   было бы нечестной постановкой эксперимента.
8. **Валидация HRV против синхронного ЭКГ** (MMSE-HR и любой другой
   датасет с параллельной ЭКГ) — прямая проверка PRV≈HRV гипотезы (§5.3)
   для конкретно этого пайплайна, а не апелляция только к общей
   литературе (Schäfer & Vagedes, 2013).

### 9.4 Статистический анализ

- Смешанные линейные модели (subject как random effect) при сравнении
  методов — субъекты вносят систематическую вариацию (тон кожи, форма
  лица, базовая ЧСС), которую нельзя игнорировать, усредняя по кадрам
  напрямую.
- Поправка на множественные сравнения (Holm-Bonferroni или аналог) при
  сравнении 6 методов × 3 частотных оценщиков попарно.
- Для Bland-Altman — явная проверка гомоскедастичности разброса ошибки
  по уровню ЧСС (см. 9.3, п.1) стандартными средствами (напр. regression
  разности на среднее, тест на значимость наклона).

### 9.5 Данные для валидации связи с ПТСР (отдельный трек, не то же самое, что точность BPM/HRV)

Требует отдельного, специально собранного датасета (ни один из
VIPL-HR/UBFC-rPPG/PURE/MMSE-HR не содержит клинической ПТСР-разметки):
видеозапись + синхронный ЭКГ/контактный PPG-референс + клиническая оценка
(CAPS-5 и/или PCL-5) на выборке с подтверждённым ПТСР и контрольной группе,
собранная под протоколом, одобренным IRB, с информированным согласием
(§5.4). Это отдельный, существенно более длительный и регуляторно тяжёлый
трек, который логично начинать только после того, как техническая точность
подтверждена на 9.1–9.4.

## 10. Дальнейшие направления

- **Обучаемый (deep learning) метод** как седьмая стратегия в
  `METHOD_REGISTRY`: современный ландшафт (см. **rPPG-Toolbox**, Liu et al.,
  NeurIPS 2023, унифицирующий сравнение классических методов с PhysNet
  (Yu et al., 2019), TS-CAN (Liu et al., 2020), EfficientPhys (2023),
  PhysFormer (Yu et al., 2022) и более поздними RhythmFormer/PhysMamba/
  графовыми архитектурами 2024-2026 годов) показывает, что supervised
  DL-методы, как правило, точнее классических на датасетах, где есть
  обучающая выборка, но требовательнее к данным и хуже генерализуются
  вне домена обучения без дополнительных мер. План интеграции: обучение
  в PyTorch → экспорт в ONNX → инференс через `onnxruntime` (уже
  протестирован в этой среде) при `AccelerationConfig.use_onnx_for_learned_method
  = True`, без внесения PyTorch в зависимости прод-инференса.
- **Blendshapes как источник признаков движения рта/мимики** — уже
  запрашиваются (`output_face_blendshapes`), но не используются:
  потенциальный дополнительный сигнал для SQI (напр. "говорит ли человек
  прямо сейчас" как независимая причина понизить доверие к ROI щёк).
- **Онлайн-калибровка порогов SQI по субъекту** — то, что сейчас глобальные
  пороги (`QualityConfig`), в перспективе может адаптироваться по первым
  N секундам записи конкретного человека.

## 11. Ограничения (сводно)

- HRV — это PRV, не ЭКГ-HRV (§5.3); не заявлять эквивалентность без
  прямой валидации.
- SQI снижает, но не устраняет ложные срабатывания при экстремальных
  условиях (сильная нерегулярная тряска камеры, полная окклюзия лица) —
  в таких случаях пайплайн корректно возвращает `publishable=False`, а не
  правдоподобное, но неверное число, но частота таких отказов на реальных
  "полевых" видео не измерена (только на синтетике, §8.2).
- Связь HRV с ПТСР в литературе — групповой, статистический эффект
  умеренной величины на неспецифичном маркере, не индивидуальный
  диагностический критерий (§5.2, §5.4).
- Ни один компонент этой системы не должен использоваться для принятия
  единоличных решений о состоянии человека без клинической валидации и
  участия специалиста.
